# 审查安排与旧卡恢复

执行卡交活后，自动审查预留在同一张卡上。`in_review` 表示已安排，`reviewing` 表示进行中。独立审查卡则预留 `--reviews` 指定的交付；标题不构成关联。

看板卡面、详情、`show` 和 leader 的 `list` 输出都显示 `reviewStatus`，包含审查卡号、是否自动审查，以及已经记录的审查档案。尚未指定档案的关联审查也会显示卡号。审查被阻塞时仍保留预留，避免静默多开一张。

## 避免重复审查

新建关联审查前，先看交付卡上的审查安排。已有自动审查或未结束的关联审查时，新建会拒绝，并写明已有卡号和状态。检查与插入在同一事务中进行，独立 CLI 进程同时建卡也只能成功一个。相同幂等键的重试仍返回原卡。

执行交活同样检查，包括从 `running` 首次交活。如果执行尚在进行时先建了关联审查，交活会拒绝再预留自动审查，并指出那张关联审查卡；原交付、交接和执行 run 保持不变。先归档过早建立的关联审查，再重试交活。检查与自动审查交活使用和关联建卡相同的写锁，并发进程也不能同时安排两份审查。静默自动补交活遇到已有预留也会拒绝，在日志中写明卡号，并保留执行状态。

关联审查进入 `acceptance`、`done` 或 `archived` 后释放预留。需要替换尚未结束的审查，应先结束或明确归档原审查。旧库已有的重复卡保留供核对，最早的预留获得开工资格；启动还会在异步准备后、创建 agent 前重新核对。重复 `start` 或重复执行交活也会指出已有审查。

审查安排不从标题猜测目标，最终验收仍由 leader 另做。

## 关联审查通过

当前绑定的审查者使用 `approve <审查卡> --summary "<证据>"`，或调用 `kanban_approve` 并传自己的卡号（可省略）。先通过审查卡自己的合同检查。下面条件同时满足时，还会把关联目标从 `in_review` 推进到 `acceptance`：

1. 审查卡用 `reviews` 明确指向目标，提交的 agent 及最新审查 run 与看板当前绑定一致。
2. 最新执行 run 与目标的执行 agent 绑定一致，双方实际 model 都有记录，按 trim/lower 规范化后不同。同 family 的不同 model 可以互审；不同 provider、effort 或 mode 不能让同一个 model 变成独立审查。当前档案和旧卡启动例外都不能替代缺失的运行证据。
3. 没有另一张未结束的关联审查，也没有其他关联审查或原卡自动审查留下的通过结论。已归档但记录过通过的审查仍算；归档的未完成审查、已结束的 request-changes 不算。目标原卡自身排队的自动预留不算另一份正在进行的审查。

审查结论和目标推进使用同一个 SQLite 写事务，与关联建卡、预留检查串行。目标收到 `approve` 审计事件，记录 `reviewTaskId`、`reviewCard`、`reviewerAgentId`、`reviewerRunId`、`reviewerModel`、`executorRunId` 和 `executorModel`。随后像 leader `pass` 一样通知验收并安排执行 agent 归档。目标的合同、执行绑定、交接和审查轮次保持不变；进入 `acceptance` 后不再参与自动审查调度。

条件不满足时，审查卡仍记录通过，两张卡说明目标没有推进的原因。目标仍是 `in_review` 时，说明会给出 `pass <被审卡> --note "<原因>"`，由 leader 核对后裁定；其他目标状态不变。目标不存在时，只在审查卡说明。审查者仍不能直接写被审卡，不能调用 leader 专用的 pass/accept；自己的卡号和当前 agent 权限检查保持生效。request-changes 行为不变，最终验收仍由 leader 决定。

等待 PR 检查时，批准对应的绑定 agent、审查 run 和目标交付证据保存在看板自己的 `pr_wait` 事件中。轮询结束后，在写锁内重新核对实际 run 和其他审查。审查者换绑会使待处理的提交失效，必须重新批准；目标重新交活，或旧的待处理检查没有绑定证据时，都不能自动推进目标。

## 恢复缺少历史执行证据的卡

关联目标的自动审查仍在缺少实际执行 model 或执行 run 时停止，不从当前档案名、provider、family 或旧审查 run 猜执行 model。目标不存在、执行绑定含糊时，仍须先修复证据。

leader 可以明确为已交付的旧卡指定审查档案：

```sh
paseo-kanban start DEMO_0001 \
  --profile "Review Example" \
  --reason "The imported delivery has no reliable executor model; I inspected the available artifact and selected this reviewer."
```

命令中的卡号是需要启动审查的卡：自动审查用原执行卡号，关联审查用已有审查卡号。没有 `reviews` 关联的旧独立审查卡也支持这条路，原审查者的 model 不会被当成执行者 model。旧审查卡已经归档时，可以针对既有产物新建替代审查卡，在简报中写明产物及缺失的关联，再用上述命令启动，无须重做执行。

`--profile` 和 `--reason` 必须同时给出，理由不能为空；只有有权限的 leader 能授权。档案必须是 reviewer 或面向 reviewer 的 candidate，并有明确的实际 model。缺 model 的错误会给出命令；没有执行绑定、停在 `needs_human` 的独立审查卡会在详情和启动错误中显示条件式恢复提示。其他需要人决定的问题，应先解决再用此恢复。

命令通过 `review_profile_authorized` 事件记录 leader、理由、指定档案及其 provider/model、本轮交付证据，并在审查卡及关联目标上添加可读评论。被阻塞的审查回到审查队列，旧审查 run 结束并走正常 agent 清理流程；执行证据和原交付保留。

额度、池的角色限制、provider 策略、思考深度和并发限制仍生效。等额度后重试仍固定使用授权档案，不会换成另一张可用档案。执行证据变化、新执行 run、返工或重新交活会让授权失效。执行 model 已知时仍按不同实际 model 的规则核对，异步启动期间新找回的证据也会重查；档案的实际 model/provider 改变会拒绝，须恢复档案或重新授权。

这是一条有记录的缺历史证据人工例外，不补造执行 model，也不声称已证明历史 model 独立。审查提示会明确说明限制及 leader 的理由。审查成功仍走原有裁定与验收流程，不会自动合并、发布或做最终验收。

Usage: kanban <command> [arguments] [--json]
Commands: create show list comment complete block approve request-changes link unlink grant-read revoke-read unblock wait-user unwait accept reject rework pass start archive register supervise handover project rebind purge-agents resume-cleanup native-sessions compact-events vacuum tag audit doctor ping
{leaderActionNote}
Card number: a display code such as ABC_0031 (case-insensitive; leading zeros may be dropped, e.g. ABC_31), or an old global number such as 114 or #114.
Complete: complete <card> --summary "<summary>" --handoff '{"files":[],"verification":"passed","risks":[],"waitingOn":"merge of PR <url>"}'. waitingOn is optional text. For repositories without CI, run tests and the build locally before a merge and record the results in the handoff. When waiting for a PR merge or another card, complete as usual. The card shows "Waiting on external: …" and the <leader> checks it at acceptance.
Block: block <card> --kind needs_human --reason "<the permission or user decision a person must handle>". kind accepts dependency, needs_human, capability, quota, rate_limit, transient. An executor reporting dependency for waiting on a PR or another card is refused: "That is not a block. Complete the card and say in the handoff what you are waiting for (handoff.waitingOn)." When waiting for CI, complete the card and describe it in handoff.waitingOn.
Waiting for user: wait-user <card> --decision <decision id> (the project's <leader> or the Kanban <leader>). Accepts ready or blocked(needs_human); converts the latter directly to ready with the decision hold in one transaction, without unblock. Other blocks and active cards are refused; a human block with a start claim, resumable agent or unresolved parent dependency also stays blocked. The card stays ready; the scheduler neither starts nor nudges it, and it does not count as blocked; the board and list/show display "Waiting for user: <id>". Decision ids have the form [dk]\d{4}-\d{6}-\d+: the cockpit's ids look like d1005-091216-1, the board's local list's like k1005-091216-1; anything else is refused. To lift it: unwait <card>; the card can then start as usual. Records wait_user / wait_user_cleared events. To pause a card you created, use wait-user, not block (block is only for blocks a person really has to handle).
Create with a pending decision: create ... --decision <decision id> (d1005-091216-1 or k1005-091216-1; optional, recorded in the card's created event). An AFC automatic reminder (an agent opened by a Paseo schedule, or a card whose title or brief contains "AFC automatic reminder") must pass --decision, and that id must exist in the cockpit's decisions.json (the ROLES_STATE_DIR environment variable may point at its directory) with the status decided by the user (done) (without the cockpit installed, the board's local list is checked, i.e. ids starting with k); otherwise the card is refused. Cards created by other identities are not affected.
Remove a parent: unlink <child> --parent <parent> (also accepts --parents, comma-separated or repeated; the project's <leader> or the Kanban <leader>). The card is then re-evaluated for starting.
Grant project reads: grant-read <card> --scope project (registered project <leader> or Kanban <leader> only). The card agent may show/list all project cards, including completed and archived cards, comments and redacted events. Other projects and write permissions stay unchanged. show exposes readScope; submission, completion or archive expires the grant. Card tokens, workers, reviewers, schedules and unregistered identities cannot grant it.
Revoke project reads: revoke-read <card> (same identity restrictions), restoring the original read rules immediately. grant_read/revoke_read events record actor, time, scope=project and project.
Parents when creating: --parents <card> (repeatable; --parent also works). An unfinished parent keeps the new card waiting.
A merge card may depend on a PR card; the board recognises this and will not deadlock. Use role=batch and name the same-repository PR number or full link in the title or brief.
Which card a review reviews: --reviews <card> (review cards only). When this review card requests changes, that card goes back to rework (in round 1 it goes back to the original executor if still there, or is dispatched again if that agent was archived or closed; in round 2 it stops and waits for the <leader>'s ruling, not sent back automatically), and the review card itself ends. A review card without --reviews that requests changes still goes to the <leader> for acceptance.
Accept: accept <card> (<leader> only). A temporary workspace without a remote first lands its actual feature branch on the local base. If the main directory has uncommitted changes, acceptance still succeeds and landing is queued (land_pending). A rebase conflict first sends the card back to rework, then reports the error; this does not count as a review round. If the main directory is not on the base branch, acceptance fails and the status is unchanged. Artifact acceptance is separate: accept <card> --artifact <commit|file|pull-request> [--reason "<what was checked>"]. The reason is required for a pull request. This records the acceptance commit, tree and evidence and does not merge or rebase onto the local base. A pull request or GitHub contract still has to match the card branch tip; a different commit is refused. With no temporary branch, the target is the commit checked out in the card workspace, including a detached HEAD. The recorded branch may be empty. Acceptance is refused when that commit cannot be read, and a different commit is refused. When the card already has a bound pull request, the artifact URL must name the same owner, repository and number; the check does not use the network. A card with no bound pull request still needs the pull request and a reason. It is refused without that evidence, and a missing remote does not select it. It still requires the <leader>, a card waiting for acceptance, and an approving review or lead pass when that card's role requires review. Active cards are refused and left unchanged.
Reject at acceptance: reject <card> --reason "<reason>" (<leader> only; the same scope as accept, and only executor cards waiting for acceptance). The card goes back to rework. When a card reaches acceptance, the executor agents it opened start being archived, so the original executor is not kept around for a rejection: if acceptance fails, open another card, or reject and start the card again. A review card that fails acceptance should be archived, or a new review card opened.
Rule rework: rework <card> --reason "<what to change>" [--agent <agentId>] [--count-round] (the project's <leader> or the Kanban <leader>). Applies to blocked, acceptance, reviewing, in_review and rework, and to a done card with a land conflict (it goes back to its original temporary directory to resolve the conflict); on a card already in rework it appends a ruling. A second request for changes stops the card in rework without sending it back to the executor; use this to send it back with your ruling. If the original executor is still there, the card goes back to it; if not, the agent is cleared, "what to do this round" is appended, and the card is dispatched again in its original directory. review_round is not increased unless --count-round is given. A ruling never trips the circuit breaker itself; if the card is sent back and review requests changes again, the round-3 circuit breaker is only a backstop after the ruling, not the point to step in.
Rule a pass: pass <card> --note "<reason for the ruling>" (the project's <leader> or the Kanban <leader>). blocked, reviewing, in_review and rework go straight to waiting for acceptance; the card must still be accepted afterwards. Use it at round 2 when only P2 findings remain, and open a separate card for the leftovers. You may also correct the brief first and then rule.
Review verdicts: once the reviewer calls approve or request-changes, that review agent is archived. The next review round opens a new review agent.
Start: start <card> [--force] (<leader> only). When a card that may change files is already running in the directory: if the project's parallel mode is on (the default), a temporary workspace is opened; only when parallel mode is off is the start refused, naming the card. With --always-temp on for the project, new agents all go to temporary workspaces, read-only roles use read-only copies, and reviews follow the reviewed card's temporary copy. --force is an explicit main-directory exception, recorded as main_workspace_exception; overriding an occupied directory is also recorded as forced. After the start, "a card is already running in the same working directory" is no longer shown.
Tags when creating: --tag <tag> (repeatable, or comma-separated). Dispatch picks profiles by tag:
  --tag high-risk     work touching money, permissions, data migration, security, outward contracts or irreversible operations. The stored tier is not changed. Review follows the executor family's L4 review list in order and takes the first dispatchable profile, whatever tier the card stores; the pre-start review reservation uses the same list, and if no review profile on it is dispatchable the executor does not start. Without an L4 list it falls back to the original tier and says so in the dispatch reason. The executor is still dispatched by the stored tier. The reviewer must still be from a different family than the executor.
  --tag complex-docs  complex documentation work; an explicitly configured profile rule may route it to a specialist.
  With --profile, tags are ignored and scope rules do not apply, but the pool's onlyRoles still does.
Effort when creating: --effort low|medium|high|xhigh|max
  Forces this reasoning effort on the agent of this card's own role, over the profile's own thinkingOptionId.
  The review opened after an executor card completes is not affected by this effort and still uses the review profile's own effort. Rework goes back to the original agent at the same effort.
Dispatch policy: a fresh board has no provider bans, model-generation limits, profile-name preferences or quota-pool order. Configure families, bannedProviders, profileRules and pool limits in settings when needed. Family rules can limit model prefixes, fast mode, ultra depth and missing quota snapshots. Every review still requires a different model family from its executor.
Tier when creating: --tier L1|L2|L3|L4
  Without it the dispatch matrix's defaultTier applies; without a matrix file, L2. With high-risk and no tier, L4.
  --tier L4 adds high-risk automatically. Adding high-risk to a card that already has a tier leaves the stored tier unchanged; review and the pre-start reservation still follow the executor family's L4 review list in order and take the first dispatchable profile.
Add tags: tag <card> --tag <tag> (repeatable, <leader> only). Records a tagged event. If high-risk was forgotten at creation, add it before review starts.
Register as a project's <leader>: supervise --project <full project name or short code> (the caller needs PASEO_AGENT_ID; configured projects only. Refused when the project already has a <leader> whose session is still there (not archived, not closed): ask that <leader> to run handover, or ask the Kanban <leader>; when the original <leader> is gone or the project has none, registration goes through. The Kanban <leader> can change any project's registration. Every change records supervisor_changed (old, new, operator).)
Handover: handover --project <project> --to <new agentId> [--from <old agentId>] [--dry-run] (for a <leader> switching sessions. Unfinished cards of the project (not done / archived) created by the old id are changed to the new id, each recording creator_changed (from / to / reason="<leader> switched sessions"), and the project's registered <leader> becomes the new id; without --from, the currently registered <leader> is used. Only the currently registered <leader> or the Kanban <leader> may run it; the new session itself (PASEO_AGENT_ID equals --to) may run it only when the original <leader> is gone (agent missing, archived or closed). Cards cannot be handed to agents the board dispatched. --dry-run shows without writing. --kanban-leader instead of --project changes supervisorAgentId and moves the old Kanban <leader>'s unfinished cards to the new id.)
Project working mode (changing settings is limited to the project's <leader> or the Kanban <leader>; a new, unconfigured project can only be added by the Kanban <leader> or from a terminal): project [--project <project>] [--workspace dir] [--base <branch>] [--lanes <count>] [--allow-lanes on|off] [--parallel on|off] [--always-temp on|off] [--wait-parent-pr on|off] [--code <code>] (<leader> only. Without arguments, shows the current settings. An unconfigured project uses its directory, with lanes off, parallel on, always-temp off and waiting for parent PRs to merge on. --wait-parent-pr off releases child cards as soon as the parent is accepted, without waiting for its PR to merge; an unaccepted parent still holds them. --lanes only changes the count and does not turn lanes on. Only --allow-lanes on allows lane cards: turning it on creates a new Paseo workspace and needs the user's consent. Once allowed, create a lane card with --workspace lane:<repository>@<base>. --parallel off stops diverting to a temporary workspace when the main directory is occupied; with always-temp also off, cards queue again. With --always-temp on, executor and batch cards always go to temporary workspaces, and reader, decision and independent review cards to read-only temporary copies; a review prefers to borrow the reviewed card's existing temporary workspace, and a review of an old directory card gets its own commit snapshot. The main directory belongs to the <leader>; the only exceptions are the switch being off or an explicit --force, recorded as main_workspace_exception. Rework, ruled rework and reassignment of a card that already has a temporary copy keep using that copy. Old main-directory cards, including ruled rework and reassignment, move into a temporary copy at their current commit; only the switch being off or an explicit --force keeps them in the main directory, recorded as main_workspace_exception. Resuming the original agent does not open another agent. Off by default. A project default of worktree is no longer supported. --code only changes the short code in display codes, not the sequence numbers, and must not clash with another project's.)
Rebind: rebind <card> --agent <agentId> (<leader> only. When a card was reclaimed by mistake or is blocked while its original agent is still there, binds the card back. The agent then completes through the command line with PASEO_AGENT_ID, because no new token can be issued.)
Purge agents: purge-agents <card> [--dry-run] (<leader> only. Only done or archived cards. Writes the key points into a comment and agent_purged first, then deletes by id. --dry-run only lists, deletes nothing.)
Resume cleanup: resume-cleanup <card> [--discard-unmerged] (<leader> only. After one cleanup step fails 12 times in a row, or the card's cleanup errors 12 times, the board stops retrying automatically and wakes once, then retries automatically every 24 hours (further failures do not wake). Once you have dealt with the cause and want to retry now, this clears the stop mark, the count restarts at 1, and retries begin on the next tick.)

Add `--discard-unmerged` after the card number to explicitly abandon a finished card's owned temporary branch. Only that project's registered <leader> or the global Kanban <leader> may use it; creators alone, workers, card tokens and anonymous shells cannot. The command lists full SHA/title pairs relative to the local base and records the authorizing leader. Normal cleanup runs on an eligible tick, keeps its ownership/shared-workspace/live-agent checks, removes the clean worktree and branch, and archives the workspace. The discard completion event records the leader and commits. Changed branch/base tips or uncommitted work hold cleanup until inspected and explicitly authorized again. Without this flag, not_merged keeps its existing behavior. The global Kanban <leader> can resume cleanup in every project.
Native sessions: native-sessions --sweep [--project <project>] [--limit <n>] [--offset <n>] [--dry-run] [--apply] (read-only by default; the Kanban <leader> may look at every project, project <leader>s and executors only at their own; only a <leader> may change anything). native-sessions --restore <sessionId> restores; --restore-manifest <file> [--dry-run] restores from a manual manifest (<leader> only); --reset-failed <agentId> [--dry-run] resets a failed retry (<leader> only; dry-run only shows). --reconcile-codex [--apply] is a one-off reconciliation: a pending codex row whose codex index already marks it archived is recorded as archived (dry-run by default, idempotent, reads only the codex index). --reconcile-claude [--apply] does the same for claude: a pending claude row whose original jsonl is gone and found in ~/.claude/projects-archive is recorded as archived, with the move record needed to restore it (dry-run by default; changes only the board database, never the files). --sweep also collects Claude sessions of agents that are archived but belong to no card (Kanban <leader> only, without --project); --include-tmp-sessions also lists test leftovers older than 1 day from directories under /tmp that no longer exist (not collected by default).
Compact events: compact-events [--dry-run] [--apply] [--days N] (<leader> only. The default dry-run opens the database read-only: no indexes, no migration, no tokens written; it only reports how much would be deleted and lists the old backups that would be removed. --apply first makes a consistent backup and verifies it, then migrates and deletes; afterwards only the newest 2 kanban.db.bak-* are kept in the data directory. Two kinds are deleted, only older than N days (default 30) and only for cards that are done or archived: duplicate verify_agent events (per card and agent, the first and last are kept), and purely informational events on an allow list (cleanup state and events with a commentId are not on it; the list is EXPIRING_EVENT_KINDS in server/compact-events.ts; the three summary events native_session_skipped, native_session_project_dir_removed and tmp_cleaned are kept only 7 days, or --days when smaller).) Source audits in write_audits expire after 30 days by default (--days also adjusts this period), including orphan and unfinished-card calls. Dry-run reports them separately; apply deletes only audits included in the backup. Cards, comments and handoffs remain.
Vacuum the database: vacuum [--dry-run] [--apply] (<leader> only. Stop the plugin first: paseo plugin disable paseo-kanban. The default dry-run only shows usage, size and free pages; --apply backs up first, then runs quick_check, VACUUM, quick_check, checks every table's row count is unchanged, and prints the size before and after. Refuses when another process holds the database. Afterwards: paseo plugin enable paseo-kanban.)
Doctor: doctor [--last] (read-only. A summary for people; --json for machines; --last shows the most recent report. Changes no cards, deletes nothing, wakes nobody. Commands in the suggestions are for a person to run.)

Identity:
- With KANBAN_TOKEN: the identity in the token.
- Without KANBAN_TOKEN but with PASEO_AGENT_ID (a malformed one is refused outright):
  - An agent the board opened (it appears in runs.agent_id, tasks.agent_id, tasks.executor_agent_id or tokens.agent_id, or carries the kanban=1 label): that card's role; it cannot create, accept, unblock, archive or start cards.
  - A registered <leader> (a project's supervisors.<project>, or the Kanban <leader> supervisorAgentId): <leader>, with this agentId in the identity; create records this agent as the card's creator.
  - An agent opened by a Paseo schedule (it carries the paseo.schedule-id label): only list, show and create (the project must be configured, no --reviews, the brief via --brief, not --brief-file); its cards are accepted by that project's <leader>.
  - Anyone else (an unregistered session): read-only, only list, show and doctor; to become a <leader>, run supervise first, or have the original <leader> or the Kanban <leader> hand over to you.
- Neither (you are running it yourself in a terminal): <leader>, with no limit on which projects you may work on.
- A <leader> with an agent identity may only accept, unblock, archive and start cards it created, or cards of projects it is registered for as <leader>.
- Create, register and changing a project's working mode: the project must be configured (from a terminal too); a <leader> with an agent identity may only do this in its own registered projects, the Kanban <leader> in any project. Adding a parent (link): the child card must be one you created or one of your project's cards; the same goes for the card named by --reviews. register, rebind and rework --agent cannot bind an agentId registered as a <leader>.
- supervisorAgentId is the Kanban <leader> (fallback), not the default <leader> of every project. It is woken only when a project's <leader> cannot be found, and the card still counts as unattended. It does not accept on behalf of other projects; blocks caused by the board (nobody can be dispatched, the circuit breaker, a card still not completed after a nudge) it may unblock across projects. rework and pass let it rule across projects; any other <leader> with an agent identity must be the registered <leader> of that project — having created the card is not enough.
- Any subcommand with --help or -h only prints this text and changes no cards. complete and approve need a non-empty summary; request-changes, block, reject and rework need a non-empty reason, pass a non-empty note. Unknown arguments are errors.

Risk: processes running as the same system user can still read the token file and the database. These rules guard against mistakes, not against deliberate circumvention.
